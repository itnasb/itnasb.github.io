Unsafe UploadStored XSS and Remote Code Execution Through Unrestricted File Upload

Application Security Training File Upload Stored XSS Remote Code Execution Web Application

Summary

This Crevice Testbed lab demonstrates an unrestricted file upload vulnerability. The application accepts user-supplied files, stores them in a web-accessible location using the supplied filename, and returns a link that allows the uploaded file to be requested afterward. Because the handler doesn’t meaningfully restrict dangerous file types, uploaded HTML can execute in the browser as stored XSS and uploaded PHP can execute on the server as remote code execution.

This lab is useful because it shows how file upload is treated by vulnerability scanners as a single issue category when it is really a delivery mechanism for several different classes of impact. It’s up to the tester to demonstrate the actual severity of the issue. If the application lets users upload browser-executable content, the result may be XSS. If it lets users upload server-executable code into a reachable location, the result may be full code execution. Same feature. Different consequences. Much worse day.

Lab Objectives

  • Identify unrestricted file upload behavior
  • Understand why filename sanitization isn’t the same as file validation
  • Observe how uploaded files are stored and served back to users
  • Recognize how uploaded HTML can produce stored XSS
  • Recognize how uploaded PHP can produce remote code execution
  • Understand why upload security depends on validation, storage location, and server behavior together

Technical Walkthrough

The application accepts a file upload and stores the uploaded file using the original filename supplied by the user. The handler removes null bytes and path separators from the name, but it doesn’t restrict dangerous extensions or inspect the uploaded content. 

$orig = basename((string)$_FILES['file']['name']);
$orig = str_replace(["\0", "/", "\\"], "", $orig);

if (move_uploaded_file($_FILES['file']['tmp_name'], $uploadDir.$orig)) {

    $_SESSION['raw_name'] = $orig;
    $_SESSION['stored_for_display'] = $orig;
    $_SESSION['current_file'] = $orig;

    unset($_SESSION['decoded_name']);

    $msg = 'Upload OK';
} else {
    $msg = 'Upload save failed';
        }

This matters because:

  • The application accepts whatever filename and extension the user provides, aside from removing path separators and null bytes
  • The file is written directly into the upload directory under that name
  • The application returns a link that allows the user to request the uploaded file afterward

Begin by testing what kinds of files the application accepts. Since the handler performs no meaningful file validation, it’s possible to upload active content.

First, upload an .html file containing a simple JavaScript proof of concept. 

<script>alert(1)</script>

The upload succeeds and the application returns a link to view the file. When that link is opened, the browser renders the uploaded HTML document and executes the script.

This is stored XSS through file upload. The application stores attacker-controlled HTML and later serves it back in a way that allows the browser to interpret it as a page.

Next, upload a .php file containing a simple proof of concept such as: 

<?php phpinfo(); ?>

Upload again succeeds, and the application returns a link to the uploaded file. When that file is requested, the server executes the PHP code and returns the resulting output.

Now the issue is no longer just stored XSS or unsafe content hosting. It’s remote code execution. The application has allowed a user to place server-executable code into a reachable location and then trigger it through a normal web request. This escalates the severity of the vulnerability from a likely medium severity to a high or critical.

Why the Logic Fails

The handler does perform a little bit of input handling, but it performs the wrong kind.

Removing null bytes and slashes from the filename helps prevent filename tricks such as path traversal, but it doesn’t make the upload safe. The dangerous part of this feature is that the user controls what type of file is stored and then gets to retrieve it from a location where the browser or server will execute it. 

accept uploaded file
strip a few unsafe filename characters
save file using user-controlled name
make file reachable after upload

There’s no allowlist for safe file types. There’s no content inspection. There’s no filename randomization. There’s no separation between uploaded content and executable web content.

A safer design would assume all uploaded files are untrusted and treat them accordingly:

  • allow only a small set of safe file types
  • validate content, not just extension
  • rename files before storage
  • store uploads outside the web root when possible
  • serve them back as downloads rather than executable content
  • disable script execution in upload directories

Not doing this is how you end up hosting attacker-controlled HTML one minute and executing attacker-controlled code the next.

Key Takeaways

  • Filename sanitization isn’t the same as upload security
  • Removing slashes from a filename doesn’t prevent dangerous file types from being uploaded
  • Unrestricted file upload can lead to stored XSS when uploaded HTML is rendered by the browser
  • Unrestricted file upload can lead to remote code execution when uploaded server-side code is stored in an executable location
  • Upload security requires validation, controlled storage, and safe serving behavior
  • User uploads should never be trusted simply because they arrived through a normal application feature
