Access Control Clues in Client-Side CodeA Burp Suite BCheck that flags authorization-related strings in Code to guide manual testing

Burp Suite BCheck Access Control Authorization JavaScript Analysis Web Security Testing

Summary

This Burp Suite BCheck was created to streamline my workflow when reviewing client-side JavaScript.The check passively scans JavaScript responses for strings that may indicate access control or authorization-related functionality, such as admin, permission, and auth.

Applications often include dozens or hundreds of JavaScript files, and manually inspecting each one can be time-consuming. This check helps prioritize files that may contain logic related to administrative functionality or authorization checks, warranting manual review.

Technical Rationale

During testing, I discovered that an application relied solely on client-side code to enforce authorization while server-side checks were absent. By reviewing the app's' custom JavaScript, I found administrative logic that relied on client-controlled values to determine privilege levels. Because these checks were not validated by the server, I was able to modify the values and perform administrative actions while authenticated as a low-privileged user, resulting in a privilege escalation vulnerability.

This inspired the creation of the BCheck. During reconnaissance, client-side code often contains references to roles, permissions, or administrative functionality. By highlighting these indicators automatically, the check helps direct attention to JavaScript files that may contain authorization logic worth reviewing more closely.

Detection Strategy

The BCheck runs passively and inspects responses whose paths end in .js. When a JavaScript file is identified, the response body is searched for several case-insensitive strings associated with authorization logic:

  • admin
  • permission
  • auth

If any of these strings appear in the file, the BCheck generates a low-confidence finding indicating that the JavaScript file may contain functionality related to access control. The alert encourages the analyst to manually inspect the file to determine whether it exposes any weaknesses.

Limitations

This check intentionally favors simplicity over precision and produces a relatively high number of false positives. Common JavaScript libraries, bundled dependencies, and unrelated variable names can easily contain these strings. In practice, the most effective way to use this check is to prioritize findings in custom JavaScript files rather than third-party libraries or frameworks.

  • Other limitations:
  • It relies on simple string matching and does not perform semantic analysis.
  • It cannot detect obfuscated or heavily minified logic.
  • It does not identify vulnerabilities directly—only potential areas of interest.

As a result, this BCheck should be viewed as a triage tool, not a vulnerability detector.

BCheck Implementation

Below is the compact BCheck implementation with inline comments explaining the detection logic. 


/*
This BCheck checks client-side scripts for strings that might hint at access control type functionality.
It will be refined in the future as it has a high rate of false positives. A workaround is to focus only on custom code.
This will only alert on low hanging fruit + any client side code with even basic obfuscation will thwart this check.
*/

metadata:
  language: v2-beta
  name: "accessControl"
  description: "Checks for strings contained in JS files that may be related to access control/authorization."
  author: "Bernard Santillan"
  tags: "passive"
	

given path then
	# if the response is a JavaScript file check for admin, permission, and auth. 
	if (base.response.url.path) matches "(?i).*\.js" then
		# only checks the response body as this is meant to drive a check of the application code 
		# and lots of response headers contain these strings.
		if (latest.response.body) matches "(?i)admin" then
			# report and continue checking for the other strings in all files. 
			# A file can contain all 3 words or none
			report issue and continue:
			name: "Check for Potential Access Control Issue"
			severity: high
			confidence: tentative
			detail: `The JavaScript file found at (base.response.url.path) contains the string "admin". Check the code to determine if it contains any access control issues.`
		end if

		if (latest.response.body) matches "(?i)permission" then
			report issue and continue:
			name: "Check for Potential Access Control Issue"
			severity: high
			confidence: tentative
			detail: `The JavaScript file found at (base.response.url.path) contains the string "permission". Check the code to determine if it contains any access control issues.`
		end if

		if (latest.response.body) matches "(?i)auth" then
			report issue and continue:
			name: "Check for Potential Access Control Issue"
			severity: high
			confidence: tentative
			detail: `The JavaScript file found at (base.response.url.path) contains the string "auth". Check the code to determine if it contains any access control issues.`
		end if
	end if
